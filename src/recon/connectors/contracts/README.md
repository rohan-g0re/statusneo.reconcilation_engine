# Interface contracts

Requirement B2 of `docs/connectivity_layer_requirements.md`:

> **B2. Interface contract documented per source.**
> Doc 2 step 2 in artefact form: endpoints or file layout, sample payload, join keys, status
> codes, **reversal semantics**, cadence. Written down per vendor, versioned with the mapping.
> *Acceptance:* every source has a contract file; a test asserts the registered schema matches
> the documented one.

One document per registered contract in `schema_registry.REGISTRY`. Each one answers, for one
vendor dataset, the six questions a connector author has to answer before writing a line of
mapping code — and then carries a seventh section that a test can read.

---

## What an interface contract is

`DOC2-002` is Doc 2's six-step connector build method. Step 2 is the discovery step: before the
adapter is built, you write down what the interface actually is. Endpoints or file layout,
a sample payload, the join keys, the status vocabularies, how a reversal is represented, and the
cadence.

The reason it is step 2 and not step 4 is that every one of those six is a thing you can be
wrong about without finding out. A wrong endpoint fails loudly on the first fetch. A wrong
reversal representation does not fail at all: you double-count or you lose a rebate, and both
look clean in every report afterwards. Writing it down is what converts an assumption somebody
holds into an assumption somebody can disagree with.

These files are the artefact form of that step. They are not documentation *about* the
connector; they are an input to it, in the same way `docs/vendor_evidence/` is an input rather
than a write-up.

## Why they are versioned with the mapping

A contract is a `(source_id, version)` pair, never a source alone.

Registering two versions of one source is normal — a vendor re-cuts its export and the old files
still have to replay. That is why `SchemaRegistry` keys on the pair, why `register(...,
current=False)` exists, and why asking for a version that is not registered raises
`UnknownSchemaVersionError` instead of falling back to the newest one. A silent fallback is
exactly how a connector validates a 2.0.0 file against the 1.0.0 contract, finds nothing wrong,
and reports success.

The document has to move with that. A contract file that described "the Craneware Claims Report"
in general would become wrong the day a second version was registered, and it would become wrong
*quietly*, because nothing reads it. So each file names its version in one place, in the exact
form the test parses, and a new version means a new registration and an updated document in the
same change.

Craneware and Verity differ in one way that matters here. **Craneware writes its version into
every row**, so the wire names its own contract and a connector passes
`version=record["schema_version"]`. **Verity writes only a record count**, so the registry has to
be told, and `version=None` resolves to the current registration. A Verity re-cut is therefore
not self-announcing, and what catches it is the field contract itself rather than a version
string.

## Why the field table is machine-checkable rather than prose

**A contract that can drift from the code is worse than no contract, because it reads as
verified.**

That is the whole argument. A prose description of a field list is read by a connector author as
a statement of fact about the running system. It was a statement of fact on the day it was
written. Nothing then connects it to the code, so it decays silently, and the reader has no way
to tell a fresh document from a stale one — both are neatly formatted markdown. The worst
outcome is not a missing document; it is a confident one that is six months behind the registry,
because the author trusts it and does not check.

So §7 of every contract file is a table with a format rigid enough to parse:

```
## Registered fields

Contract version: `craneware-sftp-export-1.0.0`

| # | field | kind | required |
|---|---|---|---|
| 1 | `record_type` | string | yes |
| 2 | `schema_version` | string | yes |
```

The rules the test enforces:

- The heading is exactly `## Registered fields`, and there is exactly one such table per file.
- The `#` column is the 1-based position and the order must match `SchemaContract.fields`
  exactly — which is also the file's column order, which is what a positional reader depends on.
- `field` equals `FieldSpec.name`.
- `kind` equals `FieldSpec.kind` verbatim, and is one of `schema_registry.KINDS`.
- `required` is `yes` or `no`, matching `FieldSpec.required`.
- The version line contains the exact registered version string in backticks.

Every table was generated by importing `schema_registry.REGISTRY` and printing it, not
transcribed by eye. Transcribing by eye is how the second row of a twenty-two row table ends up
one position out, and a table that is one position out is indistinguishable from a correct one
until someone writes a positional reader against it.

**What the table does not do** is replace the prose. It pins the shape; the surrounding sections
say what the fields mean, which values they carry, and what a connector does wrong if it
misreads them. A test can check the first and cannot check the second, which is precisely why
both are in the file.

## The contracts

| File | Source id | Vendor | Dataset or report | Contract version |
|---|---|---|---|---|
| `craneware_claims_report.md` | `craneware_claims_report` | The Craneware Group | Claims Report | `craneware-sftp-export-1.0.0` |
| `verity_accumulations.md` | `verity_accumulations` | Verity Solutions | `accumulations` | `verity-export-1.0.0` |
| `verity_invoices.md` | `verity_invoices` | Verity Solutions | `invoices` | `verity-export-1.0.0` |

Three, because three contracts are registered. The six generated feeds have no contract and are
deliberately absent from the registry — an unregistered source validates vacuously, which is what
keeps `pbm_claim_events`, `pbm_remittance_835`, `medical_837_submissions`,
`medical_835_remittance`, `tpa_340b_events` and `bank_transactions` loading exactly as they did
before the connector package existed. It is also the honest position: a contract on a generated
feed is a contract with our own generator, agreed by us on both sides. A contract on a vendor
export is a statement about a file someone else produces and can change without asking, and that
is the only kind worth registering. The generated feeds get contracts when they get a vendor.

The seven other vendor layouts the mocks write — Craneware's four remaining reports and Verity's
other three datasets — have no registered contract either, and therefore no file here. Adding one
is a `SchemaContract` and a document, in the same change.

## What is `SPEC` and what is `INVENTED`

Stated plainly, because a contract document is exactly the artefact most likely to be mistaken
for a vendor specification.

**`SPEC` — sourced to a vendor or an assessment document, cited by evidence id:**

- **The transport.** SFTP for both. `CRANEWARE-001` is Craneware's own 14 June 2023
  announcement, retrieved verbatim, naming the SFTP folder. `VERITY-001` confirms Verity Secure
  Data Transfer first-hand as automated and encrypted, though not the word SFTP, which comes from
  `DOC2-009`.
- **The absence of an API.** `CRANEWARE-005` and `DOC2-011` both record that no public customer
  API specification was found, so both connectors are SFTP-only by decision rather than by
  oversight.
- **The cadence.** `DOC2-009` gives Verity's daily / weekly / monthly. `DOC2-013` and
  `CRANEWARE-004` give Craneware's — and give it as a recommendation *to us* to ingest daily,
  not as a statement of Craneware's published schedule, which is unknown.
- **The dataset and report names.** `DOC2-009` names Verity's five datasets. `CRANEWARE-001`
  names Craneware's five reports, verbatim, including the asymmetry where "Claims Report" and
  "Bulk Dispensations Report" carry the word *Report* and the other three do not. That list is
  explicitly non-exhaustive — the source says "and other commonly requested reports."
- **The file-level controls, as a requirement rather than a shape.** `DOC2-010` asks for file
  landing, checksum, file-level idempotency and source-control totals. `CRANEWARE-004` asks for
  file-level controls and file schema versioning.

**`INVENTED` — ours, every one of them:**

- **Every field, on every contract here.** All twenty-two Craneware Claims Report fields, all
  twenty Verity accumulations fields, all twenty-two Verity invoices fields. Not one Verity
  column and not one Craneware column has any source at all.
- **Every version string.** `craneware-sftp-export-1.0.0` and `verity-export-1.0.0`.
- **Both reversal representations.** `craneware_export.REVERSAL_REPRESENTATION` and
  `verity_export.REVERSAL_REPRESENTATION`. `DOC2-011` names Verity's as unconfirmed in as many
  words; Craneware's is the same gap.
- **The file formats.** CSV with a header row, `\n` line endings, UTF-8. Verity's and
  Craneware's real formats are unknown.
- **The filenames.** Craneware's undated slugs and Verity's data-derived timestamp are both ours.
- **The trailer, the control columns and the shape of the schema version.** The vendors' sources
  imply support exists; neither shape is published.
- **The status vocabularies.** They are the TPA feed's own words, carried verbatim under
  requirement C3 precisely so nobody mistakes them for a vendor's.

The authority for all of this is `src/recon/mocks/MOCK_FIELDS.md`, which lists every column of
every vendor mock with its tier and its reasoning, and which is hand-written and never generated
— a provenance table derived from the code it audits is a table that can only ever agree with
itself. `tests/test_vendor_evidence.py` walks it: an unrecognised tier fails the build, and a
`SPEC` row citing an evidence id that is not in `docs/vendor_evidence/index.jsonl` fails the
build.

Its own summary line is the one to keep in mind while reading anything in this directory: **234
of 247 rows are `INVENTED`. The transport and the dataset and report names are the vendors'; the
fields inside them are overwhelmingly ours.**
